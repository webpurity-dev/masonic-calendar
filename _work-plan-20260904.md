# Typography Scale Rollout Plan

## Scope

Introduce a YAML-driven A6 typography scale for core calendar content. The approved reading target is 8 pt standard body text, 7 pt dense tabular content, and 6 pt secondary text. The rollout covers unit pages, contents, officer lists, succession lists, meeting tables and calendars, and membership summaries/statistics.

Extend `-section` to accept an inclusive range in the order declared by `master_v1.yaml`. For example, `-section cover-sgc_officers` will render `cover`, every intervening configured section, and `sgc_officers` as one document.

## Configuration Strategy

Store the semantic scale in `document/master_v1.yaml` under the existing `global_styling.fonts.sizes` mapping. Proposed values:

```yaml
global_styling:
  fonts:
    sizes:
      body: "8pt"
      dense_table: "7pt"
      secondary: "6pt"
```

`FontConfig.Sizes` already deserializes this mapping. `SchemaPdfRenderer` will generate CSS custom properties from the mapping, allowing templates to use semantic values such as `var(--font-body)`, `var(--font-dense-table)`, and `var(--font-secondary)`. No display value will be hardcoded in C#.

    The completed scale also defines `title: "14pt"`, `heading_primary: "12pt"`, and `heading_secondary: "10pt"`. These control document titles, `heading1`, and `heading2` respectively.

## Approach

1. Add and deserialize the scale through the existing font configuration.
2. Thread the configuration into the relevant Scriban models without changing unrelated template inputs.
3. Replace inline font sizes in the listed core templates with semantic typography values.
4. Preserve title sizes unless a proof identifies a hierarchy issue.
5. Render PDF proofs for a dense unit, officer list, contents, meeting table, and membership summary; compare legibility, wrapping, and page breaks.
6. Interpret `-section <start>-<end>` as an inclusive range of exact section IDs in their YAML declaration order. Exact section IDs continue to take precedence over section-type selection.
7. Reject unknown endpoints and reversed ranges with a clear CLI error. Render `cover-sgc_officers` as the representative range proof and verify that the first and last requested sections are present, in order, with no sections outside the range.

## Risks

- Increasing dense content to 7 pt will increase page count and may create additional page breaks.
- Fixed-width tables may wrap longer names, ranks, and unit titles; the proof set must include the densest known examples.
- Some meeting-table styles may need a separately configured compact mode if 7 pt does not fit the twelve-month grid.
- Section ranges rely on `-` as a separator; this is valid for the current underscore-based section IDs. Any future section ID containing `-` would need an explicitly chosen alternative range syntax.

## Rollback Strategy

Revert the semantic template references and remove the YAML scale. Existing inline sizes remain available in version control for precise rollback.

## Print Proof Overlays

### Scope

Separate the proof overlay modes into three independently composable CLI flags:

- `-showbleed`: draw a dotted line at the configured 3 mm trim inset, making the bleed boundary visible.
- `-showprint`: draw only configured crop marks at the trim corners.
- `-showmargins`: draw a red dotted rectangle at the configured alternating page margins.

All overlay lines will be 0.25 px wide. The 3 mm trim inset, crop-mark length, corner gap, and crop-mark color remain sourced from `master_v1.yaml`. The red margin color and 0.25 px proof line width will be added to the existing YAML `crop_marks` configuration so no display settings are hardcoded.

### Files Affected

| File | Change | Why |
|---|---|---|
| `document/master_v1.yaml` | Add YAML proof-overlay settings for line width and margin color. | Retains the project's configuration-first display policy. |
| `src/MasonicCalendar.Core/Domain/PageMargins.cs` | Add properties for the YAML proof-overlay settings. | Deserializes the configured line width and margin color. |
| `src/MasonicCalendar.Console/Program.cs` | Parse the three proof flags, pass them to the renderer, and identify them in help/output filenames. | Makes each proof overlay available independently through the CLI. |
| `src/MasonicCalendar.Core/Renderers/SchemaPdfRenderer.cs` | Generate independent bleed-boundary, crop-mark, and alternating margin CSS overlays. | Shows each production boundary accurately and allows flags to compose. |

### Approach

1. Add `proof_line_width: "0.25px"` and `margin_color: "red"` to the existing YAML crop-mark configuration.
2. Use `trim_inset` for the dotted `-showbleed` rectangle.
3. Use `mark_length`, `corner_gap`, and `color` for the `-showprint` crop marks only.
4. Use the existing alternating YAML page margins directly in side-specific CSS `inset` declarations for `-showmargins`.
5. Apply first-page margins to the cover proof, and preserve normal output when no proof flag is supplied.
6. Render both a single-page cover and a multi-page body proof with all three flags to verify positioning and composition.

### Risks

- The first-page cover margin is configured as zero, so its margin rectangle will align with the media edge.
- Paged.js class names must match the generated left/right/first page wrappers; a one-page cover and a multi-page body proof will verify this.

### Approval Status

Approved and implemented on 2026-09-04.

### Validation

- A combined `-showbleed -showprint -showmargins` cover proof verified the bleed boundary and crop marks.
- A combined `-showbleed -showprint -showmargins` `cover-master_foreword` proof verified the foreword on page 8, where normal non-zero booklet margins apply.
- The foreword proof displays the black dotted bleed boundary, black crop marks, and the red dotted YAML-driven margin rectangle together.

## Photo Page Image Expansion

### Scope

Increase the maximum image heights by 15% in the three requested static photo-page templates to use the unused lower page area. This is a template-only layout adjustment; no global or shared image values are changed.

### Files Affected

| File | Current maximum image height | New maximum image height |
|---|---:|---:|
| `document/templates/photos/photo-dpgm.html` | 51 mm top; 43 mm lower images | 58.65 mm top; 49.45 mm lower images |
| `document/templates/photos/photo-dgs.html` | 51 mm top; 43 mm lower images | 58.65 mm top; 49.45 mm lower images |
| `document/templates/photos/photo-secs.html` | 48 mm each image | 55.2 mm each image |

### Approach

1. Increase only the explicit `max-height` limits by 15%.
2. Preserve captions, gaps, widths, image aspect ratios, and page-break constraints.
3. Render the requested static section proof with `-showbleed -showmargins` and inspect the three pages for overflow or caption clipping.

### Risks

- The 15% increase could force a caption to the next page if an image reaches its new maximum height.
- Images constrained by `max-width` rather than `max-height` may not visibly enlarge by a full 15%; the proof determines the actual limiting dimension.

### Approval Status

Approved and implemented on 2026-09-05.

### Validation

- The range produced four pages because it also includes the intervening `megs_photo` section; no overflow page was created.
